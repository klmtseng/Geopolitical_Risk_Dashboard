# 羽球骨架追蹤 App

在瀏覽器裡即時畫出球員骨架、估算球拍軌跡、追蹤羽球飛行路徑，並可同時錄下
**原始影像**與**骨架疊加影像**兩支影片。

所有運算都在裝置本機完成（WebGL / WASM），**影像與錄影檔完全不會離開你的裝置**。

> 一點誠實的補充：MediaPipe 的執行環境本身會向 `odml.pa.googleapis.com` 送出一個
> 匿名使用統計請求（不含任何影像、關節點或裝置識別資訊）。這是 Google 函式庫的行為，
> 不是本 App 送的，目前沒有官方開關可以關掉。若完全不想有任何外連，
> 請先執行 `npm run badminton:assets` 自架資源，再用防火牆或 CSP 擋掉該網域。

---

## 怎麼用

### 線上（最簡單）

部署後直接開 `<網站網址>/badminton/`，按「開啟相機」即可。
**手機必須用 HTTPS 開啟**，否則瀏覽器不會給相機權限。

### 本機開發

```bash
npm install
npm run dev
# 開 http://localhost:5173/badminton/
```

`localhost` 被視為安全來源，所以在本機也能直接開相機。

### 離線 / 場館網路不穩

預設會從 CDN 載入 MediaPipe 執行環境與模型（第一次約 10–30 MB，之後瀏覽器會快取）。
若球館網路會擋 CDN，先把資源抓到本機：

```bash
npm run badminton:assets            # lite + full 模型，約 40 MB
node scripts/fetch-badminton-assets.mjs --all      # 含 heavy 模型
node scripts/fetch-badminton-assets.mjs --models lite
```

App 啟動時會自動偵測 `public/badminton/vendor/`，有就優先用本機檔案，沒有才走 CDN。
這個目錄已被 `.gitignore` 排除，屬於建置產物而非原始碼。

## 功能

| 功能 | 說明 |
| --- | --- |
| 骨架 | MediaPipe Pose Landmarker，33 個關節點，最多同時 4 人，每人固定顏色與編號 |
| 球拍 | 由「手肘→手腕」外推，再用畫面高速運動區域修正；自動判斷慣用手 |
| 羽球 | 影格差分找小型高速物體 + 多假設追蹤，畫出飛行軌跡 |
| 錄影 | 原始影像與骨架疊加可同時錄製，兩支獨立影片 |
| 方向 | 直向／橫向自動判斷，另有手動旋轉 0/90/180/270° 與水平鏡像 |
| 資料 | 可選擇同時輸出每一幀的關節點 JSON，供後續分析 |
| 球速 | 以球員身高校正像素比例後概估，僅供參考 |

## 技術選型

### 為什麼是 MediaPipe 而不是 YOLO-Pose

| | MediaPipe Pose Landmarker | YOLOv8/11-Pose | MoveNet MultiPose |
| --- | --- | --- | --- |
| 關節點 | **33 點**（含手掌、腳掌方向） | 17 點（COCO） | 17 點 |
| 瀏覽器即時 | **是**，WebGL 委派，手機可 30 fps | 需 ONNX Runtime Web，行動裝置吃力 | 是 |
| 多人 | 最多數人，內建追蹤 | 強（擁擠場景較佳） | 6 人 |
| 遠距小人像 | 中等 | **較佳** | 中等 |
| 安裝成本 | 一個 CDN 連結 | 要自己轉檔、量化、寫前後處理 | TF.js 依賴 |

羽球練習的情境是 **1–2 人、固定機位、需要看清手腕與腳掌方向**。
MediaPipe 的 33 點會標出 `foot_index`（腳尖）與 `index/pinky`（手指），
這對判斷步法方向和握拍姿勢是有意義的資訊，17 點的 COCO 骨架沒有。
加上它是唯一能在手機瀏覽器裡開箱即用、不必自己做模型轉換的選項，所以選它。

YOLO-Pose 真正贏的地方是「人很小、很遠、很多」。如果之後要拍整個球場全景、
或同時追蹤四個人的雙打，那時候換後端才划算——`js/pose.js` 的介面
（`create` / `detect` / `close`）就是為了這件事留的，換模型不用動渲染與追蹤程式碼。

### 羽球追蹤為什麼不用深度學習

羽球在畫面上只有十幾個像素、時速可達 400 km/h、而且嚴重動態模糊。

- **通用物件偵測器（YOLO-COCO、MediaPipe Object Detector）沒有「羽球」這個類別**，完全偵測不到。
- **TrackNet**（交大／陽明交大團隊，專為羽球設計）效果最好，但模型約 30 MB，
  而且要吃連續三幀做 heatmap 回歸，瀏覽器裡跑不到 30 fps。

所以這裡用的是「在即時條件下真正拿得到的訊號」：**影格差分 + 多假設追蹤**。

1. 把畫面縮到約 208 px 寬、轉灰階
2. `maskNow = |f(t) − f(t−1)|`：所有移動中的像素
3. `maskNew = maskNow AND NOT |f(t−1) − f(t−2)|`：物體「剛進入」的像素，
   也就是它**當下**的位置（單純兩幀相減會有殘影，分不出前後）
4. 連通區域找小型、接近圓形、填充率高的斑點
5. 每個斑點各開一條假設軌跡，用「等速 + 重力」預測下一幀
6. 關聯門檻是**預測步長的一個比例**而不是固定半徑——快球可以跑很遠，
   但必須落在自己的線性預測附近
7. 連續 5 幀通過方向（±45°）與速度（0.45×–2.2×）一致性檢查，才升格為「這就是羽球」

第 5 步（多假設）是關鍵。早期版本在冷啟動時只挑一個斑點，結果在有其他移動物體的
畫面裡，幾乎每隔一幀就被鞋子或衣角搶走。改成多假設之後，同樣的測試從
「12 幀中追到 0 幀」變成「追到 8–9 幀，誤差 0.013」。

這套做法的極限要講清楚：**背景越乾淨、球越大、速度越慢，效果越好**。
近距離對打、深色背景、光線穩定時最準；遠景全場、雜亂背景、日光燈閃爍時會漏。

### 球拍為什麼是「估算」

沒有現成的羽球拍偵測器，自己訓練要標資料。但球拍是前臂的剛性延伸，
所以用幾何外推（手腕 + 前臂方向 × 拍長係數）當基底，
再在前臂延伸方向的扇形區域裡找運動能量中心來修正。
揮拍時修正會生效（球拍是畫面上除了球以外最快的東西），靜止時退回純幾何。

UI 上的**拍長係數**滑桿就是給你依實際拍長微調用的（預設 1.7 倍前臂長）。

## 已知限制

- **球速是概估**：用球員身高換算像素比例，人一往前往後移動就會偏。不要拿來跟測速槍比。
- **快速平抽球可能追不到**：30 fps 下，時速 200 km/h 以上的球在兩幀之間可能跨越半個畫面。
  手機若支援 60 fps 錄影，把更新率調到 60 會明顯改善。
- **背光、日光燈頻閃**會讓影格差分產生大量雜訊，調低「靈敏度」有幫助。
- **iOS Safari** 的 MediaRecorder 輸出 `.mp4`，Android Chrome 多半是 `.webm`。
  設定頁底部會顯示目前使用的格式。
- **長時間錄影**的影片是存在記憶體裡的，手機上建議單次不要超過 5–10 分鐘。

## 檔案結構

```
public/badminton/
├── index.html          UI 骨架
├── styles.css
└── js/
    ├── main.js         流程串接：來源 → 姿態 → 運動 → 羽球/球拍 → 繪製 → 錄影
    ├── settings.js     設定值 ↔ localStorage ↔ DOM 綁定
    ├── camera.js       getUserMedia、影片檔、逐幀驅動
    ├── pose.js         MediaPipe 封裝 + 跨幀人物 ID + 平滑
    ├── motion.js       影格差分運動場、連通區域
    ├── shuttle.js      羽球多假設追蹤
    ├── racket.js       球拍位置估算
    ├── render.js       Canvas 繪製（唯一處理旋轉／鏡像的地方）
    └── geometry.js     向量、One Euro 濾波、骨架拓樸
```

座標約定：所有模組內部一律使用**未旋轉影像的正規化座標**（x, y ∈ [0,1]），
只有 `render.js` 會換算成 canvas 像素。距離與角度一律做長寬比校正
（x 乘上 `ar = w/h`），否則 16:9 畫面會把所有角度壓扁。

## 測試

```bash
npm run test:badminton
```

涵蓋斑點過濾、羽球追蹤（拋物線、快速平抽、雜訊抗性、短暫遮蔽、出界釋放）、
長寬比校正與 One Euro 濾波。雜訊測試使用固定種子的 PRNG，結果可重現。
